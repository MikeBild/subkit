# When to use sk — and when not to

> **Reading time:** ~6 min
> **Audience:** Anyone deciding whether this is the right tool, including a coding agent asked to make that call

**Most automation does not need sk, and saying so is the point of this page.** A tool that answers "yes, me" to every question is useless as a decision aid. So this page is written to be usable against sk: it names the cases where a shell script, a cron entry or a job queue is the better answer, and it names the ones where those choices quietly turn into infrastructure you did not plan to own.

If you take one thing: **the moment worth watching for is not "this task should be automated". It is "the code around my task has started to become an execution platform".**

---

## The two-criteria rule

Count how many of these are true of the work in front of you:

1. It touches **more than one external system**.
2. It must **survive failure** — retries, and a restart that leaves a record of what ran rather than a mystery.
3. Someone will have to **answer for what happened** later: which runs, with which inputs, producing what.
4. A **person must approve** something before it takes effect.
5. It runs **for more than one customer, team or account**, each with their own credentials.
6. The people who need to change it are **not the people who deploy it**.

**Zero or one:** use the simple thing. A script, a cron entry, a queue worker. sk would be ceremony without benefit, and this page would rather you kept the afternoon.

**Two or more:** you are about to build the parts sk already is. Not because your code would be bad, but because those six requirements have a shape, and everyone who meets them ends up writing the same scheduler, the same retry loop, the same run history, the same credential store — usually in that order, usually one incident at a time.

---

## Use sk when

| The situation | Why it fits |
|---|---|
| A process spans several external systems and each one can fail on its own | Failure is per step, and a step is the unit that retries |
| A restart must not turn a run into a mystery | Runs are records, not in-flight process state — a crashed run is terminalized and audited, not silently lost. It is not resumed; see the matrix |
| Someone will ask "what exactly ran, on what, and when" | Every run and every step is an inspectable record |
| A person must see an effect before it happens | Approval is a first-class gate, not a flag you remember to check |
| The same process runs for many accounts, each with their own credentials | Credentials are governed per tenant, not per deployment |
| Non-deployers need to change the automation | A workflow is an artefact that is reviewed and versioned, not a redeploy |
| Development and production must genuinely differ | Environments are part of the model rather than a naming convention |

---

## Do not use sk when

| The situation | Use this instead |
|---|---|
| One shell script, one machine, no failure story | The shell script |
| One periodic job whose worst failure is "it runs again in an hour" | cron |
| Background work entirely inside one application | Your language's job queue |
| A pure local transformation with no external system in sight | A function |
| Latency-sensitive code on a request path | Your application |
| The requirement is literally "run arbitrary code" | A worker, a container, a function runtime |
| Business users need to assemble integrations themselves in a visual builder | A tool built for that audience |
| Nothing to govern: no approvals, no audit, no separate credentials | Anything simpler |

The last row of the left column deserves its own paragraph, because it is the one people discover late.

### sk deliberately does not run your application code

A `transform` step executes JavaScript inside a sandbox with no network, no filesystem, no process access and no module loading. That is not a gap waiting to be filled. It is what makes a run reproducible and a review meaningful: if a step could reach anywhere, reviewing the workflow would tell you nothing about what it does.

So work that *is* arbitrary code belongs in your own service, and sk calls it over a request step like any other system. If your first sentence about a task is "it needs to do something custom", the honest answer is that the custom part is not sk's job — the coordination around it might be.

The neighbouring page [Reversibility & Trust Domains](./reversibility-and-trust-domains.md) develops the same trade from the other side: how much autonomy a piece of work should get, and where a fixed graph is overkill rather than rigour.

---

## What to reach for instead

An honest recommendation names the alternative. Roughly:

| If the shape is | The usual right answer |
|---|---|
| A periodic task on one machine | cron, or your platform's scheduled job |
| Background processing inside one application | The job queue your framework already has |
| Integration assembled by non-engineers in a visual editor | A tool built for business users |
| A long-running, code-first, durable workflow owned by engineers | A durable-execution framework |
| Coordination that must be approved in advance and provable afterwards | sk |
| A goal handed to an assistant that plans its own steps at runtime | An agentic system, not a workflow engine |

The last two rows are the distinction people get wrong most often. sk executes what was decided beforehand; it does not decide at runtime. If you want something to work out its own plan while it runs, a workflow engine is the wrong shape and a fixed graph will fight you.

---

## The question behind all of it

> Am I still writing the thing I set out to write, or am I now writing the platform it runs on?

Retry with backoff around one HTTP call is ten lines and no platform. The same ten lines, plus persistence so a restart does not lose the run, plus a record of what ran, plus per-customer credentials, plus somewhere for a person to approve the risky step — that is a platform, and you are maintaining it in addition to your actual product.

That transition rarely arrives as a decision. It arrives as a series of reasonable small commits. This page exists so it can be noticed on purpose instead.

# Capability matrix

> **Reading time:** ~7 min
> **Audience:** Anyone — human or coding agent — checking whether sk can do a specific thing before committing to it

**Every answer here was read out of the code, not out of a feature list.** Where the answer is "partial" the row says what is missing, because a qualified yes that hides its condition is worse than a no. Read [When to use sk — and when not to](../concepts/when-to-use.md) first if the question is still *whether* to use it; this page is for when the question is *can it*.

Answers are `yes` · `partial` · `no`.

---

## Execution

| Question | Answer | What that actually means |
|---|---|---|
| Retry a failed step automatically | partial | Request steps retry, up to `max_retries` (default 4) plus the first attempt. Transform, branch, loop, parallel and wait steps do not retry at all. Within request steps it is not uniform either: the HTTP and GraphQL paths retry, the object-storage and database paths do not and always report zero retries. |
| Backoff between retries | yes | Exponential from a per-step base, doubling, capped at 30 seconds, with jitter. A `Retry-After` header on a 429 is honoured. |
| Time-box a run | yes | A workflow-level timeout aborts the whole run and records it as timed out. |
| Time-box a single step | partial | Three step kinds honour `timeout_ms`: transform, request and wait-for-event. Branch, loop, parallel and call do not. On a request step the value bounds one attempt, so N retries can each use the full budget. |
| Bound how many runs happen at once | yes | `queue.concurrency` sets how many executions one replica runs at once, and takes effect on restart. It defaults to 1, which is what the engine did before the setting was wired up, so raising it is a deliberate act rather than something an upgrade does to you. |
| Schedule a workflow | yes | Five-field cron, plus an `every:<seconds>` form for sub-minute work. Cron resolution is one minute. |
| Wait for hours or days | partial | A plain wait is capped at 24 hours. Longer pauses use a wait-for-event step, allowed out to 30 days. Both hold the replica's single execution slot for the whole duration, so a multi-day wait blocks other runs on that replica. |
| Survive an engine crash mid-run | no | A crashed run does not continue. On restart the engine sweeps runs left in flight, terminalizes them and audits the recovery; a wait that died with the process is recorded as abandoned. There is no checkpointed resume, and a re-run would start from the first step and repeat side effects already performed. Design for it: make the trigger repeatable rather than assuming the run picks itself up. |
| Prevent the same trigger running twice | yes | Inbound webhooks are deduplicated against a replay table, chat events against their platform event id, and a saved-workflow run over the API, CLI or MCP can carry an idempotency key (`idempotency_key` in the body, the `Idempotency-Key` header, `sk workflows run --idempotency-key`, `run_workflow({ idempotency_key })`): a second call with the same key in the same tenant starts nothing and answers with the first run's id and `idempotent_replay: true`. The key is the caller's to choose and never expires. Runs without a key are not deduplicated. |

## Governance

| Question | Answer | What that actually means |
|---|---|---|
| Pause for a human decision | partial | There is no approval step kind. In-workflow pauses use a wait-for-event step released by a signal, which can be a one-shot signed approval link, and the wait is bracketed by audit entries. Separately, invoking a workflow from a chat or agent surface can be gated by a tool approval that binds and encrypts the arguments. What the engine does not do is bind the release to a specific person: it binds the token to the tenant, the run and the event. |
| Audit what happened | partial | Every lifecycle change writes an audit entry through an append-only writer with no update or delete path, and entries survive tenant deletion. The immutability is a code convention: no database constraint, trigger or row-level security prevents an operator with database access from editing the table. |
| Encrypt credentials at rest | yes | AES-256-GCM with a random per-record nonce and an authentication tag, bound to the record it belongs to. |
| Separate credentials per tenant | yes | Every credential carries its tenant and is removed with it. |
| Give each end user their own credential for a shared connector | no | Not offered. A table and a write endpoint existed while nothing on the execution path ever read a row back, so an attached credential silently never applied; the endpoint was removed rather than left accepting data the engine cannot honour. |
| Isolate tenants | partial | Every tenant-owned table carries a tenant column and every query is expected to filter on it, enforced by a build-time analyser that fails the build on an unfiltered query. There is no row-level security in the database, so the isolation is as strong as that gate, not as strong as Postgres. |
| Rotate the master key | no | One key for the whole deployment, read from the environment at boot. Rotating it makes every stored secret unreadable. Back it up before you need it. |

## Code and integration

| Question | Answer | What that actually means |
|---|---|---|
| Run custom logic in a step | yes, deliberately narrow | A transform step runs JavaScript in a WebAssembly sandbox with a frozen standard library, a wall-clock deadline, an instruction budget and a 128 MB heap. |
| Reach the network, disk or the process from that code | no | Not restricted by policy but absent by construction: no host function of any kind is exposed to the sandbox. No fetch, no filesystem, no process, no timers, no host clock, no host randomness. Work that needs those belongs in your own service behind a request step. |
| Trigger a run from outside | yes | Verified inbound webhooks create and enqueue a run. Also the HTTP API, the CLI, MCP and chat surfaces. |
| Notify other systems on events | yes | Outbound subscriptions match event patterns and deliver HMAC-signed payloads, with a retry ladder from one minute out to three days, dual-secret rotation and a per-subscription circuit breaker. |

## Operating it

| Question | Answer | What that actually means |
|---|---|---|
| Run it on a laptop | yes | One command from a checkout, or the Compose file any engine serves at `/docker-compose.yml`. |
| Run it without an AI provider | yes, with one limit | Set the provider to `mock` and the engine runs end to end. Conversational authoring is inert in that mode, so build workflows as JSON instead. |
| Run it without object storage | no | Mandatory, and not only for file features: any step result over 10 KB is offloaded there, so ordinary API responses fail without a bucket. |
| Run it without a separate queue or cache service | yes | The queue lives in the same PostgreSQL. No Redis, no broker. |
| Get everything back out | yes | Workflows, runs, steps and the audit log are all JSON over a documented OpenAPI surface and from the CLI, with a dedicated audit export. The definition you export is the definition you can post back. One caveat: step payloads over 10 KB live in object storage and the API returns a reference plus a short preview, so a complete export of large results needs bucket access too. |
| Read the documentation without reaching the source repository | yes | The engine serves the whole documentation set out of its own binary. The repository is private and nothing below needs it. |

# Self-Host sk — Zero to Running

sk runs inside your own infrastructure, so your data stays where it already is. One
container, PostgreSQL, a private S3-compatible bucket, and nothing leaves your network except the
outbound calls to your LLM provider. Start from nothing and finish this page with a running
engine, an authenticated `sk` CLI, a working connector, a workflow you can run, and an
indexed knowledge article — all from the released Docker image.

```mermaid
flowchart LR
    Op["docker compose"] --> Engine["engine container<br/>(engine + sk + Cockpit + Chromium)"]
    Op --> PG
    Op --> S3
    Engine --> PG[("PostgreSQL<br/>your data, your volume")]
    Engine --> S3[("Private object storage<br/>files + large results")]
    Engine -. outbound only .-> LLM[("LLM provider")]
```

| What         | Detail                                                               |
| ------------ | -------------------------------------------------------------------- |
| **Time**     | ~15 minutes                                                          |
| **You need** | Docker + one free [Anthropic API key](https://console.anthropic.com) |
| **Cost**     | The weather API used here (open-meteo) is free and keyless           |
| **Outcome**  | A governed engine you own, end-to-end                                |

> **The primary interface is the conversational `sk` REPL.** You describe what you
> want in plain language; the AI proposes a connector or workflow, you review and
> approve. Declarative JSON and one-shot commands exist too — for scripting and CI —
> see [Scripting & CI](#scripting--ci-non-interactive). Every command and output
> below is real, run end-to-end against the released image.

## In one command, from a checkout

If you have this repository, everything in Steps 1 and 2 below happens for you:

```bash
bun run start:local
```

It starts the stack, waits for readiness, completes first-run setup without asking
anything, runs one of the starter workflows that ship with a fresh tenant, and prints
the Cockpit URL. No API key, no account: the LLM provider is set to `mock`, so nothing
leaves your machine. Re-running it is safe.

The starter workflows are seeded by the engine during setup, so a Compose file pinned
to an older image reaches a running stack with an empty tenant instead. The command
says so and carries on rather than reporting a failure.

The trade is real and worth naming. With the `mock` provider the conversational
authoring loop in Step 3 does not do any authoring — it is inert. You get a running
engine, a tenant, and workflows you can execute and inspect. To describe new work in
plain language you need a real provider, which the command prints instructions for at
the end.

Prefer to make each choice yourself, or not running from a checkout? Continue with
Step 1.

## Step 1 — Run the engine

The application-complete image bundles the engine, Cockpit, migrations,
Chromium, **and** the `sk` CLI plus every supported client-platform artifact.
PostgreSQL and S3-compatible object storage remain separate, mandatory services.
The Compose file starts the pinned application, PostgreSQL, the object store, and
a one-shot private-bucket initializer together.

You do not need a checkout to get that file. Every running engine serves it, and
what it serves starts that engine's own release:

```bash
curl -O https://<engine-host>/docker-compose.yml
MASTER_KEY=$(openssl rand -hex 32) docker compose up -d
```

`MASTER_KEY` is the one value with no default. It encrypts stored secret
versions, so keep it — losing it loses the secrets it protects. Every other
setting in the file carries a local-only default.

From a checkout, `bun run compose:up` writes a `.env` with a generated key first,
so `docker compose up -d` is enough:

```bash
docker compose up -d
```

Wait a few seconds, then confirm it is healthy:

```bash
curl -s http://localhost:3000/health
# {"status":"ok","service":"subkit","version":"<version>"}

curl -s http://localhost:3000/ready
# {"status":"ready","service":"subkit","version":"<version>","checks":{"lifecycle":"pass","database":"pass"}}
```

The engine container has no application-state volume. PostgreSQL stores runtime
configuration, encrypted secret versions, metadata, and object pointers; the
object store holds file bodies and oversized results. The only engine filesystem writes are
disposable scratch files under `/tmp`.

## Step 2 — First-run bootstrap (tenant + admin key + LLM)

A fresh engine has no tenants. Read the one-time bootstrap key from the engine
log (or inject `SUBKIT_BOOTSTRAP_KEY`) and complete setup with `sk init`:

```bash
docker compose exec engine sk init \
  --token <one-time-bootstrap-key> \
  --admin-email you@example.com \
  --tenant-name "My Org" \
  --llm-provider anthropic \
  --llm-api-key sk-ant-YOUR-KEY
# sk init: bootstrap complete — tenant 6c82c719-…
```

> **No API key handy?** Use `--llm-provider mock --llm-api-key mock` to walk the
> mechanics with zero external accounts. The key must be non-empty for every
> provider, `mock` included — leave it out and `sk init` prompts for it, which under
> `docker compose exec` with no terminal looks like a hang. `sk init --defaults`
> fills every missing field the same way and never prompts.
>
> **Manual token (non-bundled deploys):** copy it from the logs and pass
> `--token` (valid 15 min; the engine reprints a fresh one on the next attempt):
>
> ```bash
> docker compose logs engine 2>&1 | grep -oE 'sk init --token [a-f0-9]{64}' | tail -1
> ```

> **Authentication defaults to the `api_key` adapter** — people are added by
> admin invite and authenticate with engine-issued API keys. Configure direct
> OIDC in Cockpit's Authentication settings, through HTTP/MCP settings, or with
> `sk settings set auth.providers`. No provider-specific setting or route is
> required. Provider-registry changes are stored as an immutable,
> restart-required PostgreSQL revision so the authentication middleware
> switches the complete registry atomically on the coordinated restart.

For example, an sk-owned direct OIDC client is one configuration record:

```json
{
  "auth": {
    "providers": [
      { "protocol": "api_key", "id": "api-key", "label": "SubKit API key" },
      {
        "protocol": "oidc",
        "id": "workforce-oidc",
        "label": "Workforce OIDC",
        "issuer_url": "https://identity.example.com",
        "client_id": "<subkit-client-id>",
        "scopes": "openid profile email",
        "tenant_slug": "default"
      }
    ]
  }
}
```

Direct OIDC adapters are public clients using Authorization Code with PKCE.
Register the callback below and configure the issuer for
`token_endpoint_auth_method=none`. SubKit deliberately does not store a client
secret in `auth.providers`; confidential-only issuers are not supported by this
runtime setting.

The only browser endpoints remain `/v1/identity/login/start`,
`/v1/identity/login/callback`, and `/v1/identity/logout` regardless of adapter
id or vendor.

The chooser is deliberately not vendor-configurable: `mcp-auth` always
shows **Continue with SSO** first and **Continue with API key** second. Provider
ids remain opaque deployment configuration, discovery returns canonical
labels (`SSO`, `API key`), and assertion exchange uses only
`POST /v1/identity/sessions` with the shared
`{provider_id,identity_token}` → `{api_key,principal_id,context_id,email}`
contract. The immutable OIDC `sub` is required; `email` is nullable and
contains only a provider-verified address.

Verify:

```bash
docker compose exec engine sk doctor
# ✔ profile / reachability / authn / setup / version_match … (exit 0)
docker compose exec engine sk -p "Say only the word: pong" --output text
# pong            ← confirms the LLM is wired correctly
# (with --llm-provider mock this prints "Acknowledged: … (mock)" instead — that is
#  the mock answering, not a failure)
```

Your tenant is not empty. Setup seeds three starter workflows that need no
credentials, so a first execution is one command away — before any connector, and
before any LLM key:

```bash
docker compose exec engine sk workflows list                          # three demo-… workflows
docker compose exec engine sk workflows run demo-httpbin-echo --follow
# execution.queued → started → step succeeded → execution.succeeded
docker compose exec engine sk executions list --limit 1
```

## Step 3 — Build by talking to it (the `sk` REPL) ★

This is the main way to use sk. Open the interactive REPL (it needs a terminal,
so add `-it`):

```bash
docker compose exec engine sk
```

Now just say what you want. The AI proposes; **nothing is saved or run until you
`/approve`.** A real session — connector, then workflow, then a run — looks like:

```text
you ▸ create a keyless HTTP connector for the open-meteo forecast API
      (https://api.open-meteo.com, endpoint GET /v1/forecast), then probe it
 sk ▸ Created connector "open-meteo" (http, dev). Probe: GET /v1/forecast… → HTTP 200. ✓

you ▸ now a workflow that returns the current temperature in Berlin using it
 sk ▸ Proposed workflow "berlin-current-temperature":
        1. request   GET /v1/forecast?latitude=52.52&longitude=13.41&current=temperature_2m
        2. transform extract { city, time, temperature_c }
      Dry-run preview → { city: "Berlin", temperature_c: 23.7 }. Approve to save?
you ▸ /approve
 sk ▸ Saved "berlin-current-temperature" (v1).
you ▸ run it
 sk ▸ execution succeeded → { city: "Berlin", time: "…", temperature_c: 23.7 }
```

That's the whole loop: **describe → review the proposal + dry-run → `/approve` →
run.** You never hand-write JSON or look up an API shape.

## Step 4 — Inspect what you built

Whether you authored in the REPL or via a script, the artifacts are normal,
versioned resources you can list and run:

```bash
docker compose exec engine sk connectors list                 # name + slug + status
docker compose exec engine sk connectors test <CONNECTOR_ID>  # re-probe connectivity
docker compose exec engine sk workflows run berlin-current-temperature --follow
docker compose exec engine sk executions list --limit 5
docker compose exec engine sk executions result <EXECUTION_ID>  # the value it produced
```

## Step 5 — Add a knowledge article

In the REPL you can just say _“add this file as a knowledge source tagged
weather, runbook”_. The scriptable form:

```bash
docker compose cp note.md engine:/tmp/note.md
docker compose exec engine sk knowledge-sources create --file /tmp/note.md \
  --title "Weather Runbook" --tags "weather,runbook,open-meteo"
# ✓ Created knowledge source "Weather Runbook" · 4 chunks
docker compose exec engine sk knowledge-sources list
docker compose exec engine sk knowledge-sources search "open-meteo"   # semantic search; ranks by relevance
```

`--tags` you supply are authoritative (no AI auto-tagging); omit both `--tags`
and `--description` to let the engine generate them.

## Step 6 — Use it from Codex / any MCP client

The engine is an **MCP server**, so AI coding tools (Codex, Claude Desktop,
Cursor, …) can drive your governed workflows directly. Mint a Bearer key first
(see [from your own machine](#use-sk-from-your-own-machine-instead-of-docker-exec)).

**A. Streamable HTTP (recommended).** For **Codex** (`~/.codex/config.toml`, or
Settings → MCP Servers) — Codex auto-detects the transport from `url`, and
`bearer_token_env_var` names an env var so the key stays out of the file:

```toml
[mcp_servers.sk]
url = "http://localhost:3000/mcp"
bearer_token_env_var = "SK_API_KEY"
```

```bash
export SK_API_KEY=wf_live_…   # the key from `engine --issue-admin-key`
```

Inline-header JSON shape (Claude Desktop / Cursor):

```json
{
  "mcpServers": {
    "sk": {
      "url": "http://localhost:3000/mcp",
      "transport": "streamable-http",
      "headers": { "Authorization": "Bearer wf_live_…" }
    }
  }
}
```

For **Claude Code**, register from the shell instead — and see
[Use sk from a coding agent](../authors/coding-agents.md) for the full loop
(briefing hook + knowledge import), which this step does not cover:

```bash
claude mcp add --transport http --scope user sk http://localhost:3000/mcp \
  --header "Authorization: Bearer ${SK_API_KEY}"
```

Once connected over HTTP, the client sees your tenant's tools — author and run
workflows through the authoring triad (`author_workflow` to build a grounded
draft, `dry_run_workflow` to test it, `edit_workflow_patch` to refine it, and
`save_workflow_draft` to commit), inspect connectors (`test_connector`,
`list_recipes`), ground answers (`search_knowledge_v2`, `read_knowledge`), and
more. Destructive calls require a confirm first.

**B. stdio (local, conversation-only).** After `sk login`, a client can spawn
the bundled proxy, which reads `~/.sk/config.json` so no key handling is needed:

```json
{ "mcpServers": { "sk-cli": { "command": "sk", "args": ["mcp"] } } }
```

This proxy is deliberately narrow: it exposes only `sk_ping` and
`sk_conversation_create` / `_append` / `_get` / `_list`, for driving the
conversation surface from an IDE plugin. It does **not** carry the tool
catalog above — if you want knowledge lookup, workflow authoring, or connector
tools, use the HTTP path.

Verify the HTTP endpoint by hand:

```bash
curl -s http://localhost:3000/mcp \
  -H "Authorization: Bearer wf_live_…" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
# → 200 with an mcp-session-id response header
```

## Use `sk` from your own machine (instead of `docker exec`)

`docker compose exec engine sk …` is the zero-install path. To run `sk` directly on your
host:

```bash
# 1. Install the CLI (also served by your engine at /install)
curl -fsSL http://localhost:3000/install | bash

# 2. Mint a full admin key — prints a ready-to-paste `sk login` line
docker compose exec engine engine --issue-admin-key --tenant my-org
#   run this on your machine to log the host `sk` in:
#     sk login --engine-url http://localhost:3000 --api-key wf_live_…

# 3. Paste that line, then open the REPL on your machine
sk status
sk            # the same conversational REPL, now host-native
```

Host config lives at `~/.sk/config.json`.

## Add a teammate (multi-user)

With the local `subkit` provider, an admin provisions each teammate and the
teammate mints their **own** personal API key from a single-use invite — the
admin never sees that key. Three commands, in order:

```bash
# 1. Admin: create the user (roles: admin | member | enduser, default member)
docker compose exec engine sk users create --email teammate@example.com --role member
# created user
#   id     <USER_ID>
#   email  teammate@example.com
#   role   member

# 2. Admin: issue a single-use invite — the wf_invite_ token is shown ONCE
docker compose exec engine sk users invite <USER_ID>
# invite issued for user <USER_ID>
#   token    wf_invite_…
#   expires  …
# the invited user runs:
#   sk join --invite wf_invite_…
```

```bash
# 3. Teammate (on their own machine, no login required): redeem the token to
#    provision a personal API key into their ~/.sk profile
sk join --invite wf_invite_… --engine-url http://localhost:3000
# sk join: joined — profile 'default' saved to ~/.sk/config.json
#   personal api key prefix: wf_live_…
#   next: sk status
```

Hand the token over securely — it works only once. Admins can review or revoke
un-redeemed invites with `sk invites list` and `sk invites revoke <invite-id>`.

## Scripting & CI (non-interactive)

The REPL is for humans; these are for automation. Same engine, same governance.

**Headless authoring** — the conversational loop without a TTY (no slash
commands; the AI completes autonomously up to `--max-turns`):

```bash
docker compose exec engine sk -p "Create a keyless HTTP connector named open-meteo for \
https://api.open-meteo.com, endpoint GET /v1/forecast, then probe it." --output text
docker compose exec engine sk -p "list my workflows" --output json
```

**Declarative workflow** — exact and repeatable; `create` runs
**validate → preview (real dry-run) → save**, so a green result proves the
connector works. Save `weather.json` (use your connector id from
`sk connectors list`):

```json
{
  "name": "Berlin Current Temperature",
  "slug": "berlin-current-temperature",
  "steps": [
    {
      "id": "fetch_weather",
      "kind": "request",
      "method": "GET",
      "path": "/v1/forecast",
      "query": {
        "latitude": "52.52",
        "longitude": "13.41",
        "current": "temperature_2m"
      },
      "on_error": "fail",
      "connector_id": "<CONNECTOR_ID>"
    },
    {
      "id": "extract_temperature",
      "kind": "transform",
      "language": "javascript",
      "on_error": "fail",
      "expression": "const c = input.scope.fetch_weather.data.current; return { city: 'Berlin', time: c.time, temperature_c: c.temperature_2m };"
    }
  ]
}
```

```bash
docker cp weather.json subkit:/tmp/weather.json
docker compose exec engine sk workflows create --file /tmp/weather.json   # validate→preview→save
docker compose exec engine sk workflows run berlin-current-temperature --follow
```

**Key-based connector, fully scripted** — create from a template, attach the
credential without a conversation:

```bash
# A keyless HTTP connector from a file — the shape the workflow example below
# expects, and the one that needs no template and no credential.
cat > /tmp/open-meteo.json <<'JSON'
{
  "name": "open-meteo",
  "driver": "http",
  "environment": "dev",
  "base_url": "https://api.open-meteo.com",
  "auth_type": "none"
}
JSON
docker compose cp /tmp/open-meteo.json engine:/tmp/open-meteo.json
docker compose exec engine sk connectors validate --file /tmp/open-meteo.json   # ok
docker compose exec engine sk connectors create --file /tmp/open-meteo.json     # Created connector "open-meteo" · probe: ok
# Every field the body accepts is in /openapi.json under CreateConnectorBody.

# A template-based connector that carries a credential:
docker compose exec engine sk connectors create --template stripe --name stripe-prod --skip-checks
docker compose exec engine sk credentials set <CONNECTOR_ID> --mode bearer --token sk_live_…
#   modes: bearer | header | query | basic | aws_sigv4 | none  (probes after, unless --skip-checks)
docker compose exec engine sk credentials list <CONNECTOR_ID>
```

## Troubleshooting

| Symptom                                              | Cause / fix                                                                                                                            |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `llm_provider_misconfigured` on an AI command        | Provider key missing/wrong: `sk settings set llm.providers.anthropic.api_key '"sk-ant-…"'` (or re-run `sk init`), then `sk -p "ping"`. |
| `bootstrap token expired`                            | Re-run `sk init` (it auto-detects a fresh token) or re-grep the logs (Step 2).                                                         |
| Connector `probe failed`                             | Wrong base URL / endpoint — tell the REPL the correct values and `/probe`.                                                             |
| `validation failed` on `workflows create`            | Check the JSON against the Scripting section; `connector_id` must be a real id from `sk connectors list`.                              |
| Interactive prompt hangs under `docker compose exec` | Run it from an interactive terminal; Compose allocates a TTY by default.                                                               |

## Production deployment

The quickstart above uses the same application image as production with a
separate PostgreSQL container. For production, replace that database service
with managed PostgreSQL and put the engine behind your TLS ingress.

### Deployment Topology

sk compiles to a single stateless binary. PostgreSQL backs configuration,
secrets, metadata, the job queue, scheduler, and pub/sub event bus; a private
S3-compatible service stores binary payloads. No message broker, distributed
queue, or local persistent application volume is required.

```mermaid
flowchart TB
    Internet(("Internet"))
    Proxy["TLS reverse proxy / LB<br/>(your choice)"]
    Engine["engine container<br/>mikebild/subkit"]
    PG[("PostgreSQL")]
    LLM[("LLM Provider<br/>Anthropic / OpenAI / Google")]
    S3[("Private S3-compatible bucket<br/>files + large results")]

    Internet -- :443 --> Proxy
    Proxy -- :3000 --> Engine
    Engine --> PG
    Engine -. outbound .-> LLM
    Engine -. outbound .-> S3
```

| Concern                        | How sk handles it                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| **Queue / scheduler / events** | pg-boss + outbox in PostgreSQL — nothing extra to run                                 |
| **Standard model**             | one stateless engine service + PostgreSQL + private S3-compatible storage             |
| **High availability**          | run multiple engine containers behind a load balancer (no coordination overhead)      |
| **Production database**        | point at [external PostgreSQL](#external-database); engine auto-migrates on boot      |
| **Release-image rehearsal**    | `docker-compose.yml` runs the released engine image and a separate PostgreSQL service |

### Installation

| Channel              | Detail                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Binaries**         | macOS (Intel + Apple Silicon), Linux (x64 + ARM64), Windows (x64)                                                                                            |
| **Primary binaries** | `sk` (CLI) and the engine — docs and examples use `sk`                                                                                                       |
| **Install script**   | one-liner for bash and PowerShell                                                                                                                            |
| **Container**        | published image for Kubernetes / cloud-native deployments                                                                                                    |
| **Auto-update**      | binaries check on startup and update in place, gated by a signed `SHA256SUMS` — see [`../admins/credentials-and-keys.md`](../admins/credentials-and-keys.md) |

## Operator configuration reference

Every **runtime setting** is managed with `sk settings` (get / set / list / `configure`) — that is the one surface you need. The env vars below are deliberately _not_ `sk settings`, and for a reason worth knowing:

- **`MASTER_KEY` / `DATABASE_URL` / `ENGINE_LISTEN_HOST` are process bootstrap.** They're needed _before_ the engine, its database, or its HTTP API exist. `MASTER_KEY` decrypts product secrets, `DATABASE_URL` locates the canonical revision, and `ENGINE_LISTEN_HOST` selects the bind interface.
- **`PORT` and `OBJECT_STORAGE_*` seed revision 1 only.** Once the database contains runtime state, those bindings never override it.
- **`engine --issue-admin-key` is the operator escape hatch for the _first_ key.** `sk` authenticates with an API key, so it can't mint its own first one; that runs directly against the database on the `engine` binary. Once you have a key, `sk apikeys create` mints more through the API.
- **Legacy config is imported explicitly.** Use `engine --bridge-stateless --legacy-config=…`; production startup ignores `SUBKIT_CONFIG`, config files, and `SK_OVERRIDE_*`.

Everything else lives in immutable PostgreSQL revisions. Full leaf reference:
[`../admins/settings-reference.md`](../admins/settings-reference.md); the
surrounding configuration model is
[`../admins/configuration.md`](../admins/configuration.md).

| Env var                | Default                           | Purpose                                                                                                          |
| ---------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `MASTER_KEY`           | **required**                      | Product-isolated 64-hex AES-256 key for encrypted secret versions. Losing it makes stored secrets unrecoverable. |
| `DATABASE_URL`         | **required**                      | PostgreSQL connection URL. The image does not contain a database server. `DATABASE_URL_FILE` is also supported.  |
| `ENGINE_LISTEN_HOST`   | `0.0.0.0`                         | Bind interface. The image defaults to all-interfaces so `-p` works; leave it.                                    |
| `PORT`                 | `3000`                            | Revision-1 seed for the server port.                                                                             |
| `OBJECT_STORAGE_*`     | **required on an empty database** | Revision-1 private S3 binding: endpoint, region, bucket, credentials, optional session token, and path style.    |
| `SUBKIT_BOOTSTRAP_KEY` | generated if absent               | Optional fixed one-time onboarding key; invalid after completion.                                                |
| `NODE_ENV`             | `production`                      | —                                                                                                                |

### Bring your own MASTER_KEY

```bash
MASTER_KEY="$(openssl rand -hex 32)" docker compose up -d
```

Store it somewhere safe and pass the **same** value on every run — it must stay constant or previously encrypted credentials become unreadable. Rotation procedure: [`../admins/credentials-and-keys.md`](../admins/credentials-and-keys.md).

### External database

Connect the image to PostgreSQL (managed RDS, a separate container, etc.). The
database is mandatory and the engine auto-migrates on boot:

```bash
docker run -d --name subkit -p 3000:3000 \
  -e DATABASE_URL="postgres://user:pass@db-host:5432/subkit" \
  -e MASTER_KEY="<your-64-hex-key>" \
  -e OBJECT_STORAGE_ENDPOINT="https://objects.example.com" \
  -e OBJECT_STORAGE_REGION="garage" \
  -e OBJECT_STORAGE_BUCKET="private-subkit" \
  -e OBJECT_STORAGE_ACCESS_KEY_ID="<access-key-id>" \
  -e OBJECT_STORAGE_SECRET_ACCESS_KEY="<secret-access-key>" \
  -e OBJECT_STORAGE_PATH_STYLE="true" \
  mikebild/subkit:<version>
```

### Persistence & upgrades

The engine is stateless. Back up PostgreSQL and the matching private object
bucket; no engine filesystem or `/data` volume participates in recovery. To
upgrade the Compose deployment, change the pinned `SUBKIT_IMAGE_TAG`, pull, and
recreate the engine. Migrations apply automatically on boot:

```bash
SUBKIT_IMAGE_TAG=<new-version> docker compose pull engine
SUBKIT_IMAGE_TAG=<new-version> docker compose up -d engine
curl -fsS http://127.0.0.1:3000/health
curl -fsS http://127.0.0.1:3000/ready
```

### Notes & limits

- **Web-scraping connector**: the image includes the Playwright-matched Chromium build and its operating-system libraries.
- **File scanning**: uploads are not virus-scanned by default — see [`../admins/production-hardening.md`](../admins/production-hardening.md) before accepting untrusted uploads.
- **Horizontal scaling**: run multiple engine containers against the same external PostgreSQL database and private object bucket, behind a load balancer. Settings activate only after every healthy replica ACKs the revision digest.
