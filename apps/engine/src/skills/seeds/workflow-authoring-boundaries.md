# Workflow Effect Boundaries

Start with **Set limits** on the workflow page: it derives limits from earlier runs or a write-held trial. Author manually only if none are found.

## Bounded report storage

When a workflow's automation review reports `dynamic_request` or `destructive_effect` on a step that uses the s3 driver, the supported remedy is exactly one thing: author `s3.scope` on that step. Nothing else removes those two codes for a storage step. `max_keys` and `paginate` are derived by the engine from the step itself — they can never be set or templated per prefix. For recurring S3 report reads and writes, inspect the current draft and its actual keys before patching. A request may propose `s3.scope: { key_prefix, max_bytes }`, plus `max_deletes` when the step removes objects: a fixed, narrow folder ending in `/`, a maximum UTF-8 write size (at most 10000000 bytes), and for a removal a maximum number of objects (at most 10000). GET, HEAD, LIST and PUT are supported; DELETE is supported only with `max_deletes`, and that ceiling is a reviewed number rather than a per-run count the engine enforces — say so plainly instead of implying the total is capped. Keep existing business folders and choose a justified file-size limit; never broaden to an entire bucket to make review pass. This binds hardest on a removal step: if one folder would have to cover every key it touches, split it into narrower per-folder removal steps rather than widening the prefix. LIST also uses fixed `max_keys` and `paginate` limits. File names and PUT contents may vary only inside the reviewed boundary. Metadata, range reads, presigned links and multipart uploads are not supported by this recurring profile.

This scope is a proposal, never permission. Prepare and preview the change, then use `review_workflow_automation` for the human's exact-version review in chat. Explain which report folder may be read or written and that saving can replace existing files there. Do not ask the user to edit JSON, choose patch indices, or understand storage protocol options. If other effects remain unsupported, diagnose those instead of claiming the whole workflow is ready.

## Bounded requests

For `dynamic_request` on an http step, add `boundary` to bound targets and body size for recurring approval. Report e-mail and content publication keep their stricter reviews. Patch only that step: `edit_workflow_patch` with `step_patches: [{step_id, op: "add", path: "/boundary", value: {variables, max_body_bytes, max_calls}}]`. `boundary` sits directly on the step beside `method` — not under `s3`, `config` or `body`. Do not change `path`, `body` or `for_each` to make it fit.

`variables` has exactly one entry per `${…}` placeholder that is a whole segment of `path` or a whole value in `query`, keyed by the expression without the `${}` — `"input.site"`, `"item.slug"`, `"scope.window.data.start"`. Use `{}` when neither varies. Placeholders in the body get no entry; the body is limited by size only. An entry is normally `{enum: [every value it may take]}`: 1 to 50 values written exactly as they are sent — letters, digits, `.`, `_`, `~`, `-`, `:` and `%XX` escapes (`123:runReport`, `https%3A%2F%2Fexample.com%2F`). For `input.*` copy the value from the saved schedule input (`list_schedules`). For `item.*` list every value the `for_each` source can yield. Never invent a value and never list more than the workflow needs: every value is a target the human approves. Only when the values cannot be listed — an id produced by an earlier step, a date or time window — use a value class instead: `{class: "uuid"}`, `"integer"`, `"identifier"` (letters, digits, `_` and `-`, up to 200 characters), `"long_identifier"` (the same characters up to 1024, for long opaque ids such as a Gmail `attachmentId`), `"date"` (YYYY-MM-DD), `"timestamp"` (UTC text ending in `Z`) `"file_name"` (one file name, exactly one dot: `my-essay.md`; never a path, so a step that addresses `folder/name.md` needs the folder as its own literal segment) or `"path"` (the whole rest of the address: `de/datenstand/`, `robots.txt`, `/`). Use `"path"` only when the step really does vary the entire path — a step that fetches whatever route an earlier step listed — and only on the LAST placeholder in `path`; anywhere else it is refused with `path_class_misplaced`, because it would swallow the literal segments after it. It approves every page on that one address, so prefer any narrower rule that fits. A window the API takes as unix seconds is `"integer"`, not `"timestamp"` — read the real value from the same step in the last real run before choosing a class. When a preview refuses a value it names the parameter, the value and the rule; change that one rule. A class approves EVERY value of that form, and the review dialog says so; prefer a list whenever one exists, and never use a class on a DELETE. A product workflow that removes the signed-in caller's own record addresses it with `${caller.subject}` or `${caller.principalId}` as a whole path segment and the rule `{caller_bound: true}`; that value comes from the authenticated caller persisted at admission, never from input, so it is allowed on a DELETE. Only these two caller expressions take `caller_bound`. `max_body_bytes` is the largest UTF-8 body the step may send (0 for a GET or HEAD, at most 10000000). Derive it from the workflow's own limits — for a list of identifiers, the batch cap times the bytes per identifier plus the fixed fields — and never from one preview or a round guess: a step is held to the boundary it declares on every run, preview included, and a request that does not fit fails with `request_outside_declared_boundary` naming the actual and the allowed size. Correct the number then; do not remove the boundary and do not shrink the workflow's output to fit a guessed limit. `max_calls` is the most requests per run (1 without `for_each`, at most 10000); it is a reviewed number the engine does not count yet — say so plainly rather than implying a hard cap. A DELETE additionally needs `destructive: true`, so a removal is never approved by omission.

Report e-mail is reviewed by recipient, not `boundary`. If a write-dependent condition prevents a preparation run (which holds writes) from observing it, declare `report_delivery: {kind: "gmail_report", to: "…", from: "…", content_type: "text/html"}`. Runtime decodes the human-approved message and rejects recipient mismatches before sending. Never widen an observable step.

Bound whole-placeholder header values with `boundary.headers`, keyed by the exact literal header name: `headers: {"Idempotency-Key": "${input.body.workId}"}` needs `boundary.headers: {"Idempotency-Key": {class: "identifier"}}`. Use `enum` or a value `class`, excluding `path` and `caller_bound`; add no `variables` entry. Name or rule changes require approval. Mixed literal/placeholder values, dynamic names and unbounded placeholder headers yield `runtime_header`; rules for literal or absent headers yield `header_boundary_mismatch`. Vault handles need no rule. Missing, repeated or out-of-rule runtime headers fail with `request_outside_declared_boundary` before dispatch.

For `url` equal to one `${input.*}` or `${item.*}` placeholder, use `boundary: {variables: {}, max_body_bytes: 0, max_calls, allowed_hosts: ["docs.example.com"]}`; no connector, `query`, `pagination`, multipart or DELETE. Only list user-named hosts: exact names, IDNA-normalized, no wildcard, scheme, port or IP; subdomains are separate. Runtime requires https without credentials or port on a listed host, else `request_host_not_allowed`. Recipes use `allowed_hosts: "${input.allowed_hosts}"` plus `install_inputs`; clone with the person's hosts in `inputs`, else `allowed_hosts_unpinned`. Without hosts the URL is refused.

A value may contain `:` and percent escapes, but percent-encoding is never a way around the one-segment rule: `%2F` is a literal character to the server, not a separator, so `a%2Fb` addresses something that does not exist and the request fails. One placeholder per segment, always. A placeholder that is only PART of a path segment (an identifier followed by `:action`, a prefix such as `team:` before an id) or several segments inside one placeholder cannot be bounded as written. Re-author minimally: let a transform, or the step that builds the `for_each` items, produce each WHOLE segment as its own value, reference each as its own placeholder, and list the full values; change nothing else. Not coverable at all yet, so do not add `boundary` and tell the user instead: a header NAME that varies, a query KEY that varies, `pagination`, and a connector that adds its own query parameters. When a step already has `boundary` and the review still reports it, the review names the reason; change that one thing. Do not add the boundary again and do not widen the `enum`.

A `call` approval includes the child's requests and pins its exact version; activating a new child version requires approval again. Review refuses archived/deleted children (`child_unavailable`), targets without exactly one fixed `workflow_id` or `workflow_slug` (`target_not_static`; no placeholders or both fields), and children that call another workflow (`child_calls_workflow`). Author `boundary` and `s3.scope` on the child's own steps in its chat, never on the call. Repair the child there; after activation, review the parent again.

Boundaries limit destinations and size, not content. If the body selects records to change or remove, tell the user before the review card; the dialog repeats this.
