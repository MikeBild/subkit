# Workflow Effect Boundaries

Start with **Set limits** on the workflow page, using earlier runs or a write-held trial. Author manually only if it finds none.

## Bounded report storage

For `dynamic_request` or `destructive_effect` on an s3 step, only `s3.scope` removes these codes. Inspect the current draft and actual keys before patching recurring report storage. Propose `s3.scope: {key_prefix, max_bytes}` plus `max_deletes` for removal: a fixed, narrow folder ending in `/`, a maximum UTF-8 write size ≤10000000 bytes, and a removal count ≤10000. GET, HEAD, LIST and PUT are supported; DELETE requires `max_deletes`. This deletion ceiling is reviewed, not enforced per run; say so plainly. Keep business folders and justify file-size limits; never widen to a bucket. Split removals across narrower per-folder steps if one prefix would otherwise cover all keys. The engine derives fixed `max_keys` and `paginate` from the step; neither can be set or templated per prefix. File names and PUT contents may vary within the reviewed boundary. Metadata, range reads, presigned links and multipart uploads are unsupported.

Scope grants no access. Preview, then use `review_workflow_automation` for human exact-version review in chat. Explain the report folder's read/write access and that saving can replace files there. Never ask users to edit JSON, choose patch indices or understand storage protocol options. Diagnose remaining unsupported effects before claiming readiness.

## Bounded requests

For http `dynamic_request`, bound targets and body size with `boundary` for recurring approval. Report e-mail and content publication retain stricter reviews. Patch only that step: `edit_workflow_patch` with `step_patches: [{step_id, op: "add", path: "/boundary", value: {variables, max_body_bytes, max_calls}}]`. `boundary` belongs beside `method`, never under `s3`, `config` or `body`. Preserve `path`, `body` and `for_each`.

`variables` has exactly one entry per `${…}` placeholder that is a whole segment of `path` or a whole value in `query`, keyed by the expression without the `${}` — `"input.site"`, `"item.slug"`, `"scope.window.data.start"`. Use `{}` when neither varies. Placeholders in the body get no entry; the body is limited by size only. An entry is normally `{enum: [every value it may take]}`: 1 to 50 values written exactly as they are sent — letters, digits, `.`, `_`, `~`, `-`, `:` and `%XX` escapes (`123:runReport`, `https%3A%2F%2Fexample.com%2F`). For `input.*` copy the value from the saved schedule input (`list_schedules`). For `item.*` list every value the `for_each` source can yield. Never invent a value and never list more than the workflow needs: every value is a target the human approves. Only when the values cannot be listed — an id produced by an earlier step, a date or time window — use a value class instead: `{class: "uuid"}`, `"integer"`, `"identifier"` (letters, digits, `_` and `-`, up to 200 characters), `"long_identifier"` (the same characters up to 1024, for long opaque ids such as a Gmail `attachmentId`), `"date"` (YYYY-MM-DD), `"timestamp"` (UTC text ending in `Z`) `"file_name"` (one file name, exactly one dot: `my-essay.md`; never a path, so a step that addresses `folder/name.md` needs the folder as its own literal segment) or `"path"` (the whole rest of the address: `de/datenstand/`, `robots.txt`, `/`). Use `"path"` only when the step really does vary the entire path — a step that fetches whatever route an earlier step listed — and only on the LAST placeholder in `path`; anywhere else it is refused with `path_class_misplaced`, because it would swallow the literal segments after it. It approves every page on that one address, so prefer any narrower rule that fits. A window the API takes as unix seconds is `"integer"`, not `"timestamp"` — read the real value from the same step in the last real run before choosing a class. Preview refusals name the parameter, value and rule; change only that rule. Classes approve EVERY matching value, as the review dialog states; prefer available lists. Never use a class on DELETE. A product workflow that removes the signed-in caller's own record addresses it with `${caller.subject}` or `${caller.principalId}` as a whole path segment and the rule `{caller_bound: true}`; that value comes from the authenticated caller persisted at admission, never from input, so it is allowed on a DELETE. Only these two caller expressions take `caller_bound`. To remove workflow-created jobs, temporary files or test records, declare `records_created: {id_path: "id"}` only on POST/PUT with `connector_id` and a fixed collection `path` without `${…}` (e.g. `/jobs`). `id_path` is a single scalar dot path to one output id; never record id lists/search results. Existing-resource targets yield `records_created_misplaced`. DELETE must use the same connector and `<collection>/${id}`, with `{created_by_workflow: true}` only on the last segment and `destructive: true`. `records_created` is part of the reviewed approval. The ledger records each created id once per workflow, connector, environment and collection. Before dispatch it refuses foreign ids (`delete_target_not_created_by_workflow`), replays deleting an already removed id without sending (`replayed: true`), and refuses ids whose deletion is unconfirmed (timeout/5xx) until a person checks (`delete_target_outcome_unknown`). Other methods, paging, retries, query values, no connector, nonfinal segments or varying collections yield `created_by_workflow_misplaced`. Never remove resources the workflow did not create or substitute a value pattern. `max_body_bytes` caps UTF-8 body size: 0 for GET/HEAD, at most 10000000. Derive it from workflow limits (identifier batch cap × bytes per identifier + fixed fields), never one preview or a guess. Every run, including previews, enforces it; `request_outside_declared_boundary` reports actual and allowed sizes. Correct the limit; never remove the boundary or shrink output to fit a guess. `max_calls` is the reviewed requests per run (1 without `for_each`, at most 10000), which the engine does not count yet; say so plainly. DELETE also requires `destructive: true`; omission never approves removal.

Report e-mail is reviewed by recipient, not `boundary`. If a write-dependent condition prevents a preparation run (which holds writes) from observing it, declare `report_delivery: {kind: "gmail_report", to: "…", from: "…", content_type: "text/html"}`. Runtime decodes the human-approved message and rejects recipient mismatches before sending. Never widen an observable step.

Bound whole-placeholder header values with `boundary.headers`, keyed by the exact literal header name: `headers: {"Idempotency-Key": "${input.body.workId}"}` needs `boundary.headers: {"Idempotency-Key": {class: "identifier"}}`. Use `enum` or a value `class`, excluding `path` and `caller_bound`; add no `variables` entry. Name or rule changes require approval. Mixed literal/placeholder values, dynamic names and unbounded placeholder headers yield `runtime_header`; rules for literal or absent headers yield `header_boundary_mismatch`. Vault handles need no rule. Missing, repeated or out-of-rule runtime headers fail with `request_outside_declared_boundary` before dispatch.

For `url` equal to one `${input.*}` or `${item.*}` placeholder, use `boundary: {variables: {}, max_body_bytes: 0, max_calls, allowed_hosts: ["docs.example.com"]}`; no connector, `query`, `pagination`, multipart or DELETE. Only list user-named hosts: exact names, IDNA-normalized, no wildcard, scheme, port or IP; subdomains are separate. Runtime requires https without credentials or port on a listed host, else `request_host_not_allowed`. Recipes use `allowed_hosts: "${input.allowed_hosts}"` plus `install_inputs`; clone with the person's hosts in `inputs`, else `allowed_hosts_unpinned`. Without hosts the URL is refused.

A value may contain `:` and percent escapes, but percent-encoding is never a way around the one-segment rule: `%2F` is a literal character to the server, not a separator, so `a%2Fb` addresses something that does not exist and the request fails. One placeholder per segment, always. A placeholder that is only PART of a path segment (an identifier followed by `:action`, a prefix such as `team:` before an id) or several segments inside one placeholder cannot be bounded as written. Re-author minimally: let a transform, or the step that builds the `for_each` items, produce each WHOLE segment as its own value, reference each as its own placeholder, and list the full values; change nothing else. Not coverable at all yet, so do not add `boundary` and tell the user instead: a header NAME that varies, a query KEY that varies, `pagination`, and a connector that adds its own query parameters. For existing `boundary`, fix only the reason review names; never add it again or widen `enum`.

A `call` approval includes the child's requests and pins its exact version; activating a new child version requires approval again. Review refuses archived/deleted children (`child_unavailable`), targets without exactly one fixed `workflow_id` or `workflow_slug` (`target_not_static`; no placeholders or both fields), and children that call another workflow (`child_calls_workflow`). Author `boundary` and `s3.scope` on the child's own steps in its chat, never on the call. Repair the child there; after activation, review the parent again.

Boundaries limit destinations and size, not content. Before review, disclose body-selected changes/removals; the dialog repeats this.
