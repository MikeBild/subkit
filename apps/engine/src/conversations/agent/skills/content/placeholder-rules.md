PLACEHOLDER RULES (workflow authoring):
- ALWAYS reference secrets via `${cred.<slug>.<field>}` — never inline an API key, token, or password. The executor substitutes these at dispatch time; the values never enter your context.
- Call `get_connector(id)` before authoring a step against it: the returned `placeholders` field lists the exact tokens wired up in this environment. Use those, do not guess field names.
- Use `${connector.<slug>.base_url}` to reference URLs and `${connector.<slug>.config.<path>}` for arbitrary config (regions, feature flags, versions).
- Use `${input.<path>}` for workflow input and `${scope.<step_id>.<path>}` for prior-step outputs. The output envelope is `{data, status_code?, headers?, error?, duration_ms}` — prior-step data lives at `${scope.<step>.data}`, NEVER bare `${scope.<step>}`.
- Use `${caller.tenantId}`, `${caller.principalId}`, `${caller.principalKind}`, `${caller.provider}` or `${caller.productId}` for authenticated identity. JSONata reads `$caller`; JavaScript transform bodies read `input.scope.$caller`. Caller is an immutable object or `null` for a trusted callerless system run; `principalKind` is `user` or `system_account`, `provider` is an open nonempty string, and `productId` is a string or null. Never read authorization identity from `${input.owner_id}`, fabricate caller input, or use `${$caller.*}`. Generic authenticated workflows also receive caller identity. User and system-account owners with the same identifier remain distinct.
- Nullable values retain their types in JavaScript/JSONata: caller.productId may be null. Text `${caller.productId}` interpolates null as an empty string; an exact-token value in type-preserving JSON remains null. With caller:null, caller-field tokens are unresolved. Guard caller and productId before constructing product paths or storage namespaces.
- Product identities execute matching saved workflows only, never inline drafts or standalone steps. Declaring `product_id` cannot grant an identity. Sensitive workflows cannot run live in chat, and their payload cannot be inspected into a draft; their `dry_run_workflow` returns metadata only, so state the remaining live verification without invented caller fixtures.
- `${scope.<step>.data}` is the raw RESPONSE BODY, which is whatever the connector returned — it may ITSELF be a wrapper. Many APIs nest their payload under their own key, so the real array/record can sit at `${scope.<step>.data.data[0]...}`, `${scope.<step>.data.results[...]}`, `${scope.<step>.data.items[...]}`, etc. Do NOT assume `.data` is the leaf and do NOT guess the inner shape from the API's docs. For ordinary workflows, run `dry_run_workflow` ONCE, then call `suggest_jsonata_paths` (or read the step's recorded output in the preview) to get the ACTUAL nested paths, and write your transform/placeholder against those. Sensitive payloads never enter this inspection flow; their metadata-only test run shows output field types and item counts, never paths filled with values. Guessing the nesting is the most common cause of a green run that returns empty output.
- The `author_workflow` pipeline and `edit_workflow_patch` refuse to persist a draft whose placeholder references do not resolve against the target environment — read `details.problems` and fix the tokens listed before retrying.

RUN WARNINGS (execution.warnings):
- When a workflow run completes and `warnings` is non-empty, the run succeeded but one or more expressions referenced an identifier that is not in scope. Typical cause: a transform uses `$scope.foo.X` but forgot `.data` between step-id and field. `$count` over an undefined path silently returns 0, so a workflow with warnings can look "succeeded with empty output".
- Recovery: read each warning's `identifier`, inspect the transform's `expression`, correct it (usually by inserting `.data`), call `edit_workflow_patch` to apply the fix, and re-run. Do not ship a workflow with warnings unless the user explicitly accepts them.
