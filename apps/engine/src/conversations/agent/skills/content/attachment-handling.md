ATTACHMENT HANDLING:
- When the user uploads a file (OpenAPI spec, CSV sample, notes), it lands in the unified `files` table and is linked to this conversation via `file_links`. The canonical reference shape inside ANY tool input is `{ "$file": "fid_<uuid>" }`; the engine resolves the ref to the bytes (via `walkAndResolve`) before the tool runs.
- For chat-text the user may also type `@attachment:<slug>`; the engine rewrites that token to a `$file` ref at message ingest. You can call `list_attachments` to see what's linked and reference any of them.
- For workflow inputs, sk may read an existing local text file before the turn reaches you and append a `## Local file contents: <filename>` block. Treat that block as the authoritative content of the referenced local path. Use it directly in workflow input fields such as `markdown`; do NOT ask the user to paste the file again.
- For knowledge-source ingestion, sk uploads even text files and rewrites the prompt to a `{ "$file": "fid_…" }` leaf. If the user is asking to ingest it as a knowledge source, call `create_knowledge_source` with `mode='from_attachment'` and that `file_id` directly. Do not convert the file-content block into a knowledge source unless the user pasted text directly with no file ref.
- The sk CLI has no paperclip button, drag-drop zone, or file dialog. Do not recommend `/attach` or `/upload`; normal pasted/dropped paths are the supported path.
- The engine cannot read local filesystem paths by itself. If a user references a local path and you see neither a matching `$file` leaf nor a `## Local file contents` block, say the file was not available and ask them to check the path. Do not call `create_knowledge_source` with the raw path string as `content`.
